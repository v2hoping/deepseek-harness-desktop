# Agent Note: The desktop records its startup to disk and reveals its window on first paint

Status: implemented

[English](2026-08-17-desktop-startup-log-and-window-reveal.md) | 中文

两项让桌面启动过程变得可观察的改动，写于一次 Windows 启动仍然既没有窗口、也没有任何证据之后。

## Problem

打包后的 GUI 应用在 Windows 上无处写 stderr。没有控制台附加到进程，因此桌面本就产出的每一条诊断——Host 自身的输出、账户插件的预置报告、启动失败的原因——都流向了没人能读的流。用户唯一能给出的报告是"有进程、没窗口"，而这与一次启动中任何一步的失败都相容：预置插件、预留端口、spawn Host、等它应答、创建窗口、加载渲染进程。

窗口本身也带着一条静默失败路径。它以 `show: false` 构造，只有在 `loadURL` 落定之后才显示；因此一个子资源迟迟加载不完的渲染进程——或者一次永远不落定的加载——会让一个已创建且功能正常的窗口永久不可见。这种状态与"应用根本没启动"无法区分。

## Decision

每个启动步骤都向平台自身日志目录下的 `startup.log` 追加一行带时间戳的记录——macOS 上是 `~/Library/Logs/DeepSeek Harness`，Windows 上是 `%APPDATA%\DeepSeek Harness\logs`——每行带有挂钟时间与自启动以来的毫秒数，因此日志显示的是哪一步卡住，而不只是哪一步是最后一步。Host 的输出与账户插件的预置报告除写入 stderr 外也记录于此。启动失败对话框会给出该文件路径，因为用户无法报告一个从未被告知位置的日志。

Host 输出的转发跨越启动阶段继续存在。监管器此前在 Host 应答后就丢弃了输出监听器，那只够解释一次失败的启动、别的都不够：加载失败的原生对话框 worker，或运行一小时后抛错的插件，写向的是打包应用没有控制台可承接的 stderr。缓冲仍只在启动期——它的存在是为了给失败的启动附上近期输出，而不是累积一个运行中 Host 的全部历史。

写日志绝不会让启动失败。它是最后手段的诊断，因此不可写的目录只会退化为丢弃行。此前启动积累的超限日志会被丢弃而非继续增长；而且由于 Host 只要还在运行就会持续产出输出，每次启动在写入时还会消耗自己的字节预算。在上限处停止会保留最早的那些行，而它们正是解释一次启动的那些行。

窗口的显示改由首次绘制（`ready-to-show`）驱动，而非由 `loadURL` 落定驱动，并配有 15 秒兜底，以及 `did-fail-load` 时立即显示。加载失败的窗口现在会带着错误出现，而不是根本不出现；`loadURL` 仍被 await，因此被拒绝的加载依然会让启动明确失败。

窗口也改为在等待 Host 之前就创建，先加载一个不含脚本、不含外部引用的启动页，待 Host 应答后再切换到它的 origin。在 Windows 上，加载 Host 的插件树并经过实时病毒扫描所需的时间长到足以让一个空荡的桌面被理解为启动失败；等待的长度并未改变，但它现在可见了。会话策略与托盘出于同样理由前移到该窗口之前——启动页也是渲染进程，因此约束渲染进程的策略必须先于它存在。

## Verification

`apps/desktop/tests/startup-log.spec.ts` 固定了记录行的顺序与时间戳格式、带堆栈的失败记录、目录创建、超限旧日志的丢弃，以及"无法写入的日志不会向调用方抛出任何东西"。

显示路径没有单元测试覆盖：它们是 Electron `BrowserWindow` 的事件接线，本包没有相应的测试设施。它们通过运行应用来验证。

## Alternatives considered

**依赖 stderr，并请用户从终端启动。** 无需新代码，也正是桌面此前的做法。从资源管理器启动的 GUI 应用没有可继承的控制台，而请用户从 `cmd` 复现一次启动失败，等于请他们运行一次与失败时不同的启动。

**用 Electron 的 `--enable-logging` 开关记录。** 内置，且能一并捕获 Chromium 内部信息。但它写的是 Chromium 选择写的内容，而非桌面自己的启动步骤，而且需要由那个本就启动不了应用的人去启用。

**构造时就显示未绘制的窗口，不向其中加载任何内容。** 直接消除"不可见窗口"这一失败，且无需启动页文档。但它在整个 Host 启动期间呈现一个空窗框，那看起来像应用卡死而非正在启动；启动页的代价只是一份很小的内联文档，却能说清这两者中正在发生的是哪一个。

**仍只在 `loadURL` 之后显示，并给它加超时。** 更接近原有行为。但 `ready-to-show` 是更早也更准确的信号：它在有内容可显示时触发，而 `loadURL` 要等到每个子资源都完成才认定页面已就绪。

## Consequences

失败的 Windows 启动现在会留下一个文件，写明抵达的最后一步及其耗时——这正是本次排查前两轮所缺的东西。每次启动都会写这个文件，所有平台皆然。

窗口现在可能在内容完全加载前就出现，因此一次缓慢的首启会显示空窗口而不是什么都没有。这是有意的取舍：先出现再填充的应用是可诊断的，而永不出现的应用不是。

日志跨启动累积直到超过上限，因此它保存的是这台机器近期的启动历史，而非仅仅当前这一次。
