## 1. 背景

### 1.1 现状

`dsh` 当前有两个面向用户的形态（见 [GUI 分层与 RPC 协议 Agent Note](../../.agents/notes/implemented/architecture/2026-07-19-gui-layering-and-rpc-protocol.zh.md)）：

- `dsh web`：启动本地 Host + `node:http` 载体，浏览器访问 `http://127.0.0.1:3080`。装配在 [`packages/bundle/web-app`](../../packages/bundle/web-app/README.md)。
- `dsh --profile headless`：无 Host、无 HTTP、无浏览器层，直接驱动 core 的 Agent/Session。

Web 形态的 UI 能力已经相当完整：`packages/client/ui-*` 下有 30+ 个界面插件（会话、轨迹、计划、技能、工作区、设置、权限预设等），并且已经存在**原生 OS 目录选择器**（[`dsh-host-directory-picker-native`](../../packages/host/directory-picker-native/README.md)），说明"Host 与用户坐在同一台机器前"已经是被承认的主流部署形态。

### 1.2 问题

把"本地 Host + 浏览器标签页"当作最终交付形态，存在以下缺口：

| 编号 | 问题 | 影响面 |
| --- | --- | --- |
| P1 | 需要先装 Node.js、再记住一条命令行 | 非开发者用户几乎无法完成安装 |
| P2 | 运行在浏览器标签页里 | 无独立窗口标识、无任务栏/Dock 图标、易被误关、与其它标签页争抢快捷键 |
| P3 | Agent 生命周期绑定终端进程 | 关掉终端窗口即中断长任务；重开需重新 `dsh web` |
| P4 | 无系统级集成 | 长任务完成没有系统通知；无托盘常驻；无开机自启；无原生菜单与全局快捷键 |
| P5 | 需要占用本机端口并处理 LAN 信任 | 端口冲突、`--trusted-host` 配置、浏览器信任围栏都是用户不该感知的负担 |
| P6 | 无自动更新通道 | 用户停留在初次安装的版本上，`npx` 用户则每次拉取都可能变更版本 |

### 1.3 机会

架构上"桌面形态"不是新增一条平行实现，而是**换一个载体（carrier）**。既有分层文档已经明确预留了这条路径：

> A future Electron application reuses the same web client packages over an IPC fetch carrier.
> —— [`2026-07-19-gui-layering-and-rpc-protocol.md`](../../.agents/notes/implemented/architecture/2026-07-19-gui-layering-and-rpc-protocol.md)

> It serves browsers only: Electron loads the built files over `file://` and sends fetch requests through an IPC bridge instead of this server.
> —— [`docs/subsystems/web-server.md`](../../docs/subsystems/web-server.md)

即：**UI 层零重写，Host 层零重写，只新增一个传输载体与一个应用装配。**

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 一键安装，零 Node.js 前置依赖 | macOS `.dmg`、Windows 安装包、Linux `.AppImage`/`.deb` 可在干净机器上双击安装并启动 |
| G2 | 与 `dsh web` 功能对等 | 现有 `packages/client/ui-*` 插件全部可用，无需为桌面分叉 UI 代码 |
| G3 | 原生系统集成 | 独立窗口、托盘、系统通知、原生菜单与快捷键、开机自启、文件/目录拖拽 |
| G4 | 后台常驻 | 关闭窗口不终止进行中的 Agent 任务；重新打开窗口可看到完整轨迹 |
| G5 | 自动更新 | 应用可检测、下载并在重启后应用新版本 |
| G6 | 不占端口、不暴露 LAN | 默认形态下不监听任何 TCP 端口 |

### 2.2 非目标

- **不重写 UI**：不引入第二套组件体系，不为桌面分叉 `packages/client/ui-*`。
- **不修改 `agent-loop`**：桌面化不触碰 core 的循环语义（见根 [`AGENTS.md`](../../AGENTS.md) 的"Plugins, not loop changes"）。
- **不做移动端**。
- **首版不做远程连接管理**：桌面客户端连接远端 Host 是明确的后续演进方向（第 8 节），首版只支持本机 Host。
- **不替换现有 `dsh web`**：Web 形态继续作为远程/容器/服务器部署的一等形态存在，两者共存。

### 4.5 验收标准

首个可用版本（M1 结束）的验收：

1. 在一台**未安装 Node.js** 的干净 macOS 与 Windows 机器上，双击安装包完成安装并启动。
2. 填入 `DEEPSEEK_API_KEY` 后，能创建工作区、发起对话、看到流式输出与完整工具轨迹。
3. 工具审批弹窗、计划模式、技能列表、设置面板与 `dsh web` 表现一致。
4. 关闭窗口后任务继续，托盘图标存在，重开窗口能看到任务已推进的轨迹。
5. 全程 `lsof -i` / `netstat` 观察不到应用监听任何 TCP 端口。
6. 原生目录选择器在三个平台上均可正常打开与取消。

## 5. 技术方案

### 5.1 架构定位

桌面形态是**第三个应用装配（application assembly）**，与 `dsh web`、`dsh --profile headless` 平级，复用同一套 Host 与 Client 包：

```
                       apps/desktop  (新增，Electron 应用)
                        ├─ main      主进程：装配 Host、窗口/托盘/菜单/更新
                        ├─ preload   contextBridge 暴露最小 IPC 面
                        └─ renderer  复用 dsh-client-web shell（等同 apps/web 的 main.ts）
                              │
        ┌─────────────────────┴─────────────────────┐
        ▼                                           ▼
packages/host/*                             packages/client/*
  apiproxy   协议前层（不变）                  ui-* 30+ 界面插件（不变）
  runtime    装配层（不变）                    connection（新增 IpcApiClient 子类）
  webserver  Web HTTP 载体（桌面不挂载）        modules（注入自定义 loadBundle）
```

三条现有约束决定了这个形状，均为既有事实：

- **协议与载体解耦**：所有客户端都继承 `AbstractApiClient`（[`packages/host/apiproxy/src/fetch/client.ts:244`](../../packages/host/apiproxy/src/fetch/client.ts)），协议不变量（rpcId 铸造、四象限信封、zod 校验、SSE 帧解码）全在基类里，平台差异只体现在抽象方法 `doFetch` 上。现有三个子类分别是 `WebApiClient`（浏览器 HTTP + WebSocket）、`InProcessApiClient`（进程内注入 handler）、`FixtureApiClient`（无服务端 UI 开发）。**桌面端只需要第四个子类，实现 `doFetch` 一个方法。**
- **Host 与载体解耦**：`dsh-host-webserver` "knows no harness concepts"，且明确声明只服务浏览器；桌面端不挂载它，因此不开端口。
- **进程内 fetch 已经存在**：`toFetchHandler(api)`（[`packages/host/apiproxy/src/fetch/handler.ts:243`](../../packages/host/apiproxy/src/fetch/handler.ts)）把 `ApiProxy` 变成一个 `fetch` 函数，走完整的真实 wire 序列化与校验。桌面端主进程持有的正是这个 handler。

### 5.2 关键技术决策

#### 决策 1：Electron，而非 Tauri

**选择：Electron。**

| 维度 | Electron | Tauri |
| --- | --- | --- |
| 主进程运行时 | Node.js，可直接在进程内挂载现有 cordis Host 图 | Rust，需另起 Node sidecar 进程承载 Host |
| Node-only 插件（`shell`/`subprocess`/`fs`/`lsp`/`terminal`） | 原生可用 | 必须全部跑在 sidecar 中 |
| 传输载体 | Electron IPC，零端口 | Rust ↔ Node sidecar 需要本地 socket/HTTP，重新引入端口与信任问题 |
| 现有 native 依赖（koffi、landlock addon） | 走 Electron 的 ABI rebuild 流程，成熟 | 仍需在 sidecar 中处理，等于两套打包 |
| 安装体积 | 较大（约 100–150 MB） | 较小（约 10–30 MB） |
| 内存占用 | 较高 | 较低 |

理由：dsh 的 Host 是一棵**必须跑在 Node 上**的 cordis 插件图，Tauri 的体积优势会被"必须外挂 Node sidecar"完全抵消，且把零端口这一核心收益（G6）也一并丢掉。体积与内存是已知代价，接受。

#### 决策 2：IPC fetch 载体，而非 localhost HTTP

桌面端**不**在主进程里起 `dsh web` 然后用窗口套一个 `http://127.0.0.1:3080`。原因：

- 端口冲突、防火墙提示、LAN 暴露面、`--trusted-host` 配置、浏览器信任围栏，全部是用户不该感知的负担（P5）。
- 走 IPC 后，请求在同一进程内经 `toFetchHandler` 完成，序列化与 zod 校验一个不少，可观测性不降级。

渲染进程通过 `file://` 加载打包的前端产物，`preload` 用 `contextBridge` 暴露一个最小的请求面（见 5.4 安全模型）。

#### 决策 3：Host 先跑在主进程，预留 `utilityProcess` 演进

**v1 选择：Host 在 Electron 主进程内运行。** 最短路径，且 `toFetchHandler` 可直接注入。

**已知风险**：主进程同时负责窗口/菜单/托盘事件循环，Host 的 CPU 密集工作（大量 diff、日志投影、压缩）可能造成 UI 卡顿。

**演进路径**：若 M1 的性能观测证实存在可感知卡顿，将 Host 迁移到 `utilityProcess`（Electron 的 Node 子进程），主进程退化为纯窗口管理 + IPC 中转。**该迁移不改变协议与 `IpcApiClient` 实现**，只把 `doFetch` 的对端从"同进程 handler"换成"跨进程消息端口"，因此不需要在 v1 提前投入。

#### 决策 4：客户端插件 bundle 的分发改道

这是唯一一处**不能靠换载体自然解决**的问题，必须实现。

既有事实：客户端插件以 `dsh.client` 双面包形式存在，其浏览器半通过 HTTP 端点 `/plugins/<id>/client.js?rev=<rev>` 拉取，端点由 [`packages/client/modules`](../../packages/client/modules/README.md) 的 node 半提供，启动清单经 `window.__DSH_BOOT__` 注入 index.html（由 webserver 的 index tap 完成）。

桌面端没有 webserver，因此需要：

1. **清单注入**：主进程在窗口加载前，通过 preload 或 `did-finish-load` 前的注入把 `__DSH_BOOT__` 送入渲染进程，替代 index tap。
2. **bundle 加载**：`ClientModuleHost` 已经暴露了可注入的 `loadBundle?: (url: string) => Promise<void>` 钩子（[`packages/client/modules/src/client/manifest.ts`](../../packages/client/modules/src/client/manifest.ts)）——这是既有扩展点，桌面端注入自己的实现即可。

   两个候选实现：
   - **自定义协议（推荐）**：注册 `dsh-plugin://` 特权协议，主进程按 id 从磁盘读取 bundle 返回。保留原生 `import()` 语义、保留 source map、保留浏览器缓存策略。
   - **IPC 取字节 + Blob URL**：兼容性最好但丢失 source map 且绕过缓存。

   **提议采用自定义协议，IPC 取字节作为兜底。**

#### 决策 5：不复用 `frontend-static`，收紧 CSP

[`dsh-host-frontend-static`](../../packages/host/frontend-static/README.md) 的 SPA 语义（miss 回落 index.html）是 HTTP 概念，`file://` 下由 Electron 的协议处理器等价实现。桌面端应用严格 CSP：禁止远程脚本、禁止 `eval`、图片与字体限本地来源。

### 5.5 安全模型

桌面应用把 Agent 的完整能力（执行 shell、读写文件系统、访问网络）装进了一个用户双击就能运行的壳里，安全配置不是可选项：

| 项 | 要求 |
| --- | --- |
| `contextIsolation` | `true`，不可关闭 |
| `nodeIntegration` | `false`，渲染进程不接触 Node API |
| `sandbox` | 渲染进程开启沙箱 |
| preload 暴露面 | 只暴露 `doFetch` 所需的最小方法集，不暴露任意 IPC 通道、不暴露 `fs`/`child_process` |
| CSP | 禁止远程脚本与 `eval`；脚本仅来自本地打包产物与插件协议 |
| 导航 | 拦截 `will-navigate` 与 `window.open`，外部链接一律 `shell.openExternal` |
| 凭据存储 | 复用 [`packages/credentials`](../../packages/credentials/README.md) 的引用式凭据模型；桌面端**提议**新增基于 Electron `safeStorage`（钥匙串/DPAPI）的 provider，避免明文落盘。待评审 |
| 工具审批 | 复用既有 `packages/interaction` 权限链路，桌面端不新增旁路 |
| 沙箱能力 | Linux 的 landlock addon（[`native/`](../../native/README.md)）与 Windows 目录选择器的 koffi 依赖必须随包正确解出，否则相关能力静默降级——见风险 R3 |

### 5.6 测试策略

对齐 [`docs/testing.md`](../../docs/testing.md)：

| 层级 | 内容 |
| --- | --- |
| 单测 | `IpcApiClient.doFetch` 的传输行为（成功、错误码、中断、SSE 帧切分）。协议不变量已由基类与既有测试覆盖，不重复 |
| 进程内协议测试 | 继续用 `InProcessApiClient` 覆盖协议本身，桌面载体不改变 wire |
| 快照测试 | **注意**：若桌面 surface 像 `web-app` 那样注册 `app:desktop-surface` prompt section，则属于模型可见变更 —— 按根 `AGENTS.md` 的"Model-visible ⟺ logged"，必须同 PR 补 session event 与 keyless snapshot |
| e2e | Electron 冒烟（Playwright 的 Electron 驱动）：启动 → 建会话 → 发 prompt → 见流式输出 → 关窗口任务续跑 → 托盘恢复 |
| 产物 smoke | CI 打包后在干净容器/虚拟机中启动一次，验证 native 依赖已正确解出 |

**现有快照与单测必须保持全绿**：桌面化若导致既有快照变更，说明改动越过了载体层，需回到本文评审。

## 6. 风险与缓解

| 编号 | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | 安装体积 100 MB+ | 下载转化率 | 接受；提供增量更新降低后续成本 |
| R2 | 主进程承载 Host 导致 UI 卡顿 | 体验 | M1 加性能观测；触发阈值则按决策 3 迁 `utilityProcess` |
| R3 | native 依赖（koffi、landlock addon）在打包后不可用 | 目录选择器与 Linux 沙箱失效 | M3 显式处理 ABI rebuild 与 asar unpack；产物 smoke 覆盖 |
| R4 | 签名证书与公证账号未就位 | 阻塞 F1.3、F1.5 | **开放问题 Q1**，需尽早启动申请 |
| R5 | Windows 杀软对未签名安装包误报 | 安装转化 | 依赖 R4 解决；发布前做主流杀软扫描 |
| R6 | 自动更新服务端托管方案未定 | 阻塞 F1.5 | **开放问题 Q2** |
| R7 | HMR 链路在桌面下语义不明 | 开发体验 | 桌面产物包默认关闭 HMR；开发模式单独走 dev server |
| R8 | 客户端插件 bundle 改道破坏 source map | 调试体验 | 采用自定义协议方案（决策 4）保留 source map |

## 8. 后续演进（不在本次范围）

- **连接远端 Host**：桌面客户端指向远程机器上的 dsh Host。`AbstractApiClient` 的载体抽象天然支持，本质是让用户在 `IpcApiClient` 与 `WebApiClient` 之间选择。
- **多 Host 管理**：一个桌面应用管理多台机器上的多个 Host。
- **系统级快捷入口**：选中文本后通过全局快捷键直接投喂给 Agent。
