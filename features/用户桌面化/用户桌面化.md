| 项 | 值 |

本需求包含两个支柱，共同服务一个目标——**让不懂 npm、不懂命令行的用户能直接用上 dsh**：

1. **桌面安装**：Electron 打包，macOS / Windows 一键安装，零 Node.js 前置依赖。
2. **账户体系**：默认走 DeepSeek 账户注册登陆，登陆即可用，用户不需要理解"什么是 API Key"。

文中区分**既有事实**（附代码行号或文档链接可核对）与**本方案设计**（待实现）。

## 1. 背景

### 1.1 现状

`dsh` 当前有两个面向用户的形态（见 [GUI 分层与 RPC 协议 Agent Note](../../.agents/notes/implemented/architecture/2026-07-19-gui-layering-and-rpc-protocol.zh.md)）：

- `dsh web`：启动本地 Host + `node:http` 载体，浏览器访问 `http://127.0.0.1:3080`。装配在 [`packages/bundle/web-app`](../../packages/bundle/web-app/README.md)。
- `dsh --profile headless`：无 Host、无 HTTP、无浏览器层，直接驱动 core 的 Agent/Session。

Web 形态的 UI 已经相当完整：`packages/client/ui-*` 下有 30+ 个界面插件，且已存在**原生 OS 目录选择器**（[`dsh-host-directory-picker-native`](../../packages/host/directory-picker-native/README.md)），说明"Host 与用户坐在同一台机器前"已是被承认的主流部署形态。

配置侧的现状对本需求非常有利：

- **设置面板是开放的**。`settings.section`（每 feature 一页）与 `settings.onboarding`（首次运行引导）都是 `kind: 'list'` 的开放 slot（[`packages/client/ui-settings/src/client/contract/slots.ts:53,73`](../../packages/client/ui-settings/src/client/contract/slots.ts)），新增页面**不需要修改设置外壳**。
- **凭据只存引用，不存值**。配置里写的是环境变量名，值由 provider 持有，且**每次模型请求重新 resolve**（[凭据子系统](../../docs/subsystems/credentials.md)）——所以账户登陆后写入的 key 立刻生效，无需重启进程。
- **可写的凭据存储已存在**。`$DSH_HOME/.credentials.yaml` 是可写层，优先级高于两个 `.env` 层（[`credentials-local`](../../packages/credentials/credentials-local/README.md)）。

### 1.2 问题

| 编号 | 问题 | 影响面 |
| --- | --- | --- |
| P1 | 需要先装 Node.js、再记住一条命令行 | 非开发者用户几乎无法完成安装 |
| P2 | 运行在浏览器标签页里 | 无独立窗口标识、无任务栏/Dock 图标、易被误关、与其它标签页争抢快捷键 |
| P3 | Agent 生命周期绑定终端进程 | 关掉终端即中断长任务 |
| P4 | 无系统级集成 | 长任务完成没有通知；无托盘常驻；无开机自启；无原生菜单 |
| P5 | 需要占用本机端口并处理 LAN 信任 | 端口冲突、`--trusted-host` 配置都是用户不该感知的负担 |
| P6 | 无自动更新通道 | 用户停留在初次安装的版本上 |
| P7 | **首次使用要求用户自备 API Key** | 小白用户需要理解"什么是 API Key"、自行去 platform 注册、创建、复制粘贴——这是当前最大的上手断点 |
| P8 | **余额、用量、账单在应用外** | 用户必须离开应用去网页查，余额耗尽时应用内只表现为请求失败 |

### 1.3 机会

架构上"桌面形态"不是新增一条平行实现，而是**换一个载体（carrier）**。既有分层文档已明确预留这条路径：

> A future Electron application reuses the same web client packages over an IPC fetch carrier.
> —— [`2026-07-19-gui-layering-and-rpc-protocol.md`](../../.agents/notes/implemented/architecture/2026-07-19-gui-layering-and-rpc-protocol.md)

而账户体系依托设置面板的开放 slot，可以做成**一个独立的新增包**，几乎不触碰现有代码。两者叠加，恰好满足 D3 的上游跟进要求。

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 一键安装，零 Node.js 前置依赖 | 三个目标平台的产物可在干净机器上下载后直接启动 |
| G2 | 与 `dsh web` 功能对等 | 现有 `packages/client/ui-*` 插件全部可用，插件化能力不退化 |
| G3 | 原生系统集成 | 独立窗口、托盘、系统通知、原生菜单、后台常驻 |
| G4 | 网页下载即用 | 从 GitHub Releases 下载的产物，用户不需要处理安全告警之外的任何步骤 |
| G5 | 不占端口、不暴露 LAN | 默认形态下不监听任何 TCP 端口 |
| G6 | **登陆即可用** | 新用户从安装到发出第一条消息，全程不需要理解 API Key 概念 |
| G7 | **账户信息应用内可见** | 余额、用量、账单、充值入口都在应用内 |
| G8 | **可跟进上游** | 官方仓库升级后，本项目能以可控成本 rebase 并重新出包 |

### 2.2 非目标

- **不重写 UI**：不引入第二套组件体系，不为桌面分叉 `packages/client/ui-*`。
- **不修改 `agent-loop`**：桌面化与账户化都不触碰 core 的循环语义。
- **不做 Linux 桌面包**：D4 明确三个目标，Linux 用户继续用 `dsh web`。
- **不做 Windows ARM64**：D4 取消适配。
- **不做自动更新**：D5 明确采用手动打包 + GitHub Releases 分发。
- **不上应用商店**：不走 Mac App Store / Microsoft Store 的审核与分发通道。
- **不做移动端**。
- **不自建支付**：充值与账单一律走官方页面。
- **不替换现有 `dsh web`**：Web 形态继续作为远程/容器/服务器部署的一等形态存在。
- **首版不做远程连接管理**：桌面客户端连接远端 Host 是后续演进方向（第 8 节）。

### 4.4 验收标准

首个可用版本（M2 结束）的验收：

1. 在一台**未安装 Node.js** 的干净 macOS 与 Windows 机器上，从下载的产物启动（Windows 解压即用，macOS 拖入 Applications），首次运行的安全告警按 F1.5 的指引可通过。
2. 首次启动弹出登陆引导，用手机号完成登陆后，应用自动准备好 apikey，**用户全程未手动接触任何 key**，随即能发出第一条消息并看到流式输出。
3. 工具审批弹窗、计划模式、技能列表、设置面板、插件清单与 `dsh web` 表现一致。
4. 账户栏五个 Tab 均可打开；状态 Tab 显示正确余额；apikey Tab 能列出并切换 key；充值/账单能打开官方页面且处于已登陆态。
5. 模型页 API Key 输入为禁用态并有提示；关闭账户支持后恢复可编辑。
6. 关闭窗口后任务继续，托盘图标存在，重开窗口能看到任务已推进的轨迹。
7. 全程 `lsof -i` / `netstat` 观察不到应用监听任何 TCP 端口。
8. 断网或内部接口失效时，登陆引导降级为手动路径，用户仍能完成配置。

## 5. 技术方案

### 5.1 桌面架构

#### 5.1.1 定位

桌面形态是**第三个应用装配**，与 `dsh web`、`dsh --profile headless` 平级，复用同一套 Host 与 Client 包：

```
                       apps/desktop  (新增，Electron 应用)
                        ├─ main      主进程：装配 Host、窗口/托盘/菜单/更新、账户后端
                        ├─ preload   contextBridge 暴露最小 IPC 面（fetch + account）
                        └─ renderer  复用 dsh-client-web shell（等同 apps/web 的 main.ts）
                              │
        ┌─────────────────────┴─────────────────────┐
        ▼                                           ▼
packages/host/*                             packages/client/*
  apiproxy   协议前层（不变）                  ui-* 30+ 界面插件（不变）
  runtime    装配层（不变）                    connection（新增 IpcApiClient 子类）
  webserver  Web HTTP 载体（桌面不挂载）        ui-account（新增，账户栏）
```

三条既有事实决定了这个形状：

- **协议与载体解耦**：所有客户端继承 `AbstractApiClient`（[`packages/host/apiproxy/src/fetch/client.ts:244`](../../packages/host/apiproxy/src/fetch/client.ts)），协议不变量全在基类，平台差异只在抽象方法 `doFetch`。现有三个子类是 `WebApiClient`、`InProcessApiClient`、`FixtureApiClient`。桌面端只需第四个子类。
- **Host 与载体解耦**：`dsh-host-webserver` 明确只服务浏览器；桌面端不挂载它，因此不开端口（G5）。
- **进程内 fetch 已存在**：`toFetchHandler(api)`（[`packages/host/apiproxy/src/fetch/handler.ts:243`](../../packages/host/apiproxy/src/fetch/handler.ts)）把 `ApiProxy` 变成 `fetch` 函数，走完整的真实 wire 序列化与校验。

#### 5.1.2 关键决策

**决策 1：Electron，而非 Tauri。**

| 维度 | Electron | Tauri |
| --- | --- | --- |
| 主进程运行时 | Node.js，可直接在进程内挂载现有 cordis Host 图 | Rust，需另起 Node sidecar 进程 |
| Node-only 插件（`shell`/`subprocess`/`fs`/`lsp`/`terminal`） | 原生可用 | 必须全部跑在 sidecar 中 |
| 传输载体 | Electron IPC，零端口 | Rust ↔ Node sidecar 需本地 socket/HTTP，重新引入端口问题 |
| native 依赖（koffi） | 走 Electron ABI 流程，成熟 | 仍需在 sidecar 中处理，等于两套打包 |
| 账户能力（持久 cookie、内嵌登陆页、子窗口） | 一等能力 | 需自行搭建 |
| 安装体积 | 较大（约 100–150 MB） | 较小 |

dsh 的 Host 是一棵**必须跑在 Node 上**的 cordis 插件图，Tauri 的体积优势会被"必须外挂 Node sidecar"抵消，并丢掉零端口收益。体积是已知代价，接受。

**决策 2：IPC fetch 载体，而非 localhost HTTP。** 桌面端不在主进程里起 `dsh web` 再用窗口套 `http://127.0.0.1:3080`。走 IPC 后请求在同一进程内经 `toFetchHandler` 完成，序列化与 zod 校验一个不少，同时消除端口冲突、防火墙提示、LAN 暴露面与信任围栏配置。

**决策 3：Host 先跑在主进程，预留 `utilityProcess`。** v1 让 Host 在 Electron 主进程内运行，最短路径。已知风险是主进程同时处理窗口事件，Host 的 CPU 密集工作可能造成 UI 卡顿。若 M2 的性能观测证实可感知卡顿，再迁移到 `utilityProcess`——**该迁移不改变协议与 `IpcApiClient` 实现**，只把 `doFetch` 的对端从"同进程 handler"换成"跨进程消息端口"。

**决策 4：客户端插件 bundle 的分发改道。** 这是唯一不能靠换载体自然解决的问题。既有事实：客户端插件的浏览器半通过 HTTP 端点 `/plugins/<id>/client.js?rev=<rev>` 拉取，由 [`packages/client/modules`](../../packages/client/modules/README.md) 的 node 半提供，启动清单经 `window.__DSH_BOOT__` 注入 index.html。桌面端没有 webserver，需要：

1. **清单注入**：主进程在窗口加载前把 `__DSH_BOOT__` 送入渲染进程，替代 index tap。
2. **bundle 加载**：`ClientModuleHost` 已暴露可注入的 `loadBundle?: (url: string) => Promise<void>`（[`packages/client/modules/src/client/manifest.ts`](../../packages/client/modules/src/client/manifest.ts)）——**这是既有扩展点**。注册 `dsh-plugin://` 特权协议，主进程按 id 从磁盘读 bundle 返回，保留原生 `import()` 语义与 source map。

这一条直接决定 G2（插件化能力不退化），是 M1 的核心验证项。

#### 5.1.3 打包硬约束

两个约束必须在 M0 前置验证，否则方案不成立：

| 约束 | 事实 | 风险 |
| --- | --- | --- |
| `node:sqlite` | `session-persistence-sqlite/src/index.ts:13` 与 `session-query-sqlite` 直接 `import 'node:sqlite'`；仓库 engines 要求 Node `^22.19 \|\| >=24` | Electron 内置 Node 必须支持 `node:sqlite`（Node 22 下为实验特性）。不满足则会话持久化不可用，必须选定满足条件的 Electron 版本 |
| koffi | 被 `fs-local`、`directory-picker-native`、`sandbox-windows-acl`、`session-persistence-jsonl` 四个包依赖，走 optionalDependencies 分平台二进制（本机仅 `@koromix/koffi-darwin-arm64`） | `.node` 文件不能从 asar 内加载，须 `asarUnpack`；三个目标平台必须各自在对应 runner 上打包（D4 取消 Windows ARM64 后，剩余三个架构均为 koffi 的一等支持目标，风险显著下降） |

#### 5.1.4 未签名产物的分发代价

D5 采用网页下载分发。**代码签名与应用商店是两件独立的事**：Mac App Store 需要审核与商店分发，而 Developer ID 签名 + 公证（notarization）恰恰是 Apple 为**商店之外的网页下载**准备的机制。不上商店并不能免除签名需求。两个平台的实际表现差异很大：

| 平台 | 未签名时用户看到什么 | 用户需要做什么 | 对小白用户的影响 |
| --- | --- | --- | --- |
| **macOS** | 从网页下载的产物带 quarantine 标记，Gatekeeper 拦截并提示"无法打开，因为无法验证开发者"（部分系统版本显示为"已损坏，应移到废纸篓"） | 到"系统设置 → 隐私与安全性"点"仍要打开"，或对文件执行 `xattr -d com.apple.quarantine` | **严重**：提示文案会让用户以为程序损坏或有毒，多数人直接放弃。与原则 4（傻瓜化）直接冲突 |
| **Windows** | SmartScreen 蓝色警告"Windows 已保护你的电脑" | 点"更多信息 → 仍要运行" | **中等**：两次点击可通过，是常见的开源软件体验 |

结论：Windows 不签名可以接受；macOS 不签名会明显抬高流失率。

两点精确性补充：Apple Silicon 要求所有 arm64 可执行文件至少带 ad-hoc 签名，electron-builder 在无证书时会自动补上，因此提示通常是"无法验证开发者"而非"已损坏"，后者多出现在签名于传输中被破坏时。另外 `com.apple.quarantine` 由**下载器**写入——浏览器、微信、邮件、AirDrop 会打上标记，而本地构建产物、`curl`/`wget` 下载、U 盘拷贝都不带。所以开发者本机双击毫无阻碍，**这正是"本地正常、用户打不开"的经典陷阱**，验收必须走真实浏览器下载路径。

#### 5.1.5 免费分发路径（D7）

调研结论：

| 平台 | 免费签名是否可得 | 说明 |
| --- | --- | --- |
| **Windows** | **可得** | [SignPath Foundation](https://signpath.io/solutions/open-source-community) 为合格开源项目提供免费 OV 级签名，私钥存于 HSM，可接入 CI。条件：OSI 许可证且无商业双授权（本项目 MIT，符合）、非恶意软件、非黑客/安全利用工具、活跃维护、已有正式发布；附加要求团队开启 MFA、定义作者/审核/批准角色、公开一份 code signing policy |
| **macOS** | **不可得** | Developer ID 证书只能由付费 Apple Developer Program 签发，且 Apple 协议**禁止用自有 Developer ID 为第三方项目签名**，因此"基金会代签"模式在 Apple 生态无法合规存在。免费 Apple 账号只能本机开发调试，不能分发、不能公证 |

两个常见误解：

- **`rcodesign`**（[apple-platform-rs](https://github.com/indygreg/apple-code-sign-action)）是完整的开源 Apple 签名与公证实现，可在 Linux/Windows 上运行、无需 Mac——它解决的是**工具链自由，不是费用**，仍需付费账号签发的证书。
- 加入 Eclipse、Apache 等基金会可由基金会以自身身份签名，但门槛远高于 99 美元，且应用显示的是基金会名义。

因此 macOS 采用三件套免费路径（按推荐顺序）：

1. **Homebrew tap**：`brew install --cask v2hoping/tap/<app>`，自建 tap 无需提交官方 cask；升级也是一条命令，正好补上 D5 不做自动更新的缺口。quarantine 的具体处理方式（cask 声明或用户加 `--no-quarantine`）在 T4.6 实测确认。
2. **一行安装脚本**：`curl -fsSL <raw-url>/install.sh | bash`，脚本内完成下载、解压、移入 Applications；`curl` 不参与 LaunchServices 机制，产物不带 quarantine 标记。
3. **兜底说明**：正常下载后若被拦，执行 `xattr -dr com.apple.quarantine /Applications/<App>.app`，在下载页写明。

一个有利的错配：**Windows 用户中小白比例高，而 Windows 恰好只需两次点击（拿到 SignPath 签名后为零）；macOS 用户中开发者比例高，而 macOS 需要一条命令。** 成本最高的平台正对应最能承受该成本的用户群。99 美元待项目取得赞助收入后再考虑。

### 5.2 账户架构

#### 5.2.1 前提：公开 API 的边界

已核实的事实——DeepSeek 公开 API 只有三个端点：

| 端点 | 用途 | 鉴权 |
| --- | --- | --- |
| `POST /chat/completions` | 推理 | API Key |
| `GET /models` | 模型列表 | API Key |
| `GET /user/balance` | 余额（`is_available`、`total_balance`、`granted_balance`、`topped_up_balance`，CNY/USD） | API Key |

**没有** OAuth、登陆、apikey 列出/创建、用量明细、账单接口。因此登陆必须走 platform 网页流程，apikey 管理必须走内部接口（决策 D1）。

#### 5.2.2 分层设计

账户能力**不进入 harness 的 RPC 协议表**，而是走 Electron 自己的 IPC 通道：

```
渲染进程                             主进程
─────────                            ─────────
dsh-client-ui-account                DeepSeekAccountBackend
  账户 section + 5 个 Tab      ←IPC→   ├─ 登陆窗口（BrowserWindow + 持久 partition）
  登陆引导 onboarding 步骤             ├─ 会话 cookie 管理
  能力探测：window.dshDesktop?.account └─ PlatformApiAdapter ← 唯一的内部接口调用点
         │                                      │
         │ 拿到 key 后                          │ 失效时降级
         ▼                                      ▼
  已有的 credentials.set RPC          引导手动创建 + 粘贴
```

这样设计的理由：

- **账户所需的能力本质上是 Electron 的**：持久化 cookie 会话、内嵌登陆页、带 cookie 的请求、子窗口——Host 侧无法提供。
- **零改动 `apiproxy`**：新增 RPC 域需要改 `rpc-map.ts`、schema、handler routes、client 方法表共 5 处现有文件，每次 rebase 都是潜在冲突点。走 Electron IPC 完全绕开。
- **与 harness 的耦合面收敛为一个点**：拿到 key 后调用**已有的** `credentials.set`，写入 `$DSH_HOME/.credentials.yaml`。凭据每次请求重新 resolve，写入即生效。
- **Web 形态自动降级**：`dsh web` 下 `window.dshDesktop` 不存在，账户 section 不注册，Web 用户看到的界面与现在完全一致（F3.4）。

#### 5.2.3 登陆的承载方式：独立窗口加载官方页面

登陆**既不用 iframe 内嵌，也不自建登陆表单**，而是打开一个**独立的 `BrowserWindow`** 加载 `https://platform.deepseek.com/sign_in`，配独立的持久 partition。三个方案的对比：

| 方案 | 可行性 | 原因 |
| --- | --- | --- |
| **iframe / `<webview>` 内嵌** | **不可行** | 登陆页普遍设置 `X-Frame-Options: DENY` 或 CSP `frame-ancestors` 以防点击劫持，嵌不进去；即便嵌进去也因跨域隔离拿不到会话 cookie；且与本方案 5.4 的渲染进程 CSP（禁止远程内容）冲突 |
| **自建登陆表单 + 调内部登陆接口** | **不可行且不应做** | 公开 API 无登陆接口；手机号验证码与微信扫码带设备指纹与行为风控，自建调用大概率被拦；更关键的是密码与验证码会流经我们的界面，用户理应怀疑凭据被截获；微信扫码还涉及微信开放平台授权，无法自建 |
| **独立 `BrowserWindow` 加载官方页**（采用） | **可行** | 顶层窗口不是 frame，不受 `X-Frame-Options` 约束；用户看到的是真正的官方页面，地址栏与 HTTPS 证书可验证，信任成立；密码与验证码只在官方页面内流转，我们碰不到；微信扫码是官方流程原样可用 |

登陆完成后，主进程从该 partition 的 cookie jar 读取会话 cookie，交给 5.2.4 的适配层使用。**不向登陆页注入任何脚本**（见 5.4 安全模型）。这也是第三方桌面客户端在没有 OAuth 时的通行做法。

由此确定账户功能的分工：

| 功能 | 承载方式 |
| --- | --- |
| 登陆、充值、账单 | 官方页面（独立窗口，共享登陆 partition） |
| 状态、用量、apikey 管理 | **自绘界面**，通过适配层调接口取数据（D1） |

#### 5.2.4 内部接口适配层

`PlatformApiAdapter` 是**唯一**允许调用 platform 内部接口的模块，职责：

- 持有登陆会话 cookie，构造带 cookie 的请求。
- 提供语义化方法：`listApiKeys()`、`createApiKey(name)`、`getAccountProfile()`、`getUsage(range)`。
- 每个方法都有明确的失败语义，失败时上抛可识别的错误类型，由上层触发降级。
- **接口路径、请求/响应结构集中在一个常量表里**，官方改版时单点修复。

内部接口的具体路径与响应结构目前未知，需要在 M3 开始前抓包确认（见执行计划 T3.1）。文档中不预设路径，避免写入猜测。

#### 5.2.5 充值与账单

不自绘。点击对应 Tab 的按钮，打开一个**共享同一登陆 session partition** 的独立窗口加载官方页面。理由：

- 支付流程涉及资金安全与合规，自建不现实也不应该。
- 共享 partition 意味着用户在这些页面上是已登陆态，无需二次登陆。
- 官方页面改版不影响我们——我们只负责打开它。

Tab 结构仍按需求保留五个（见 4.3.3），只是充值/账单两个 Tab 的内容是说明 + 打开按钮。

#### 5.2.6 模型页的接管提示

按 D2（仅 API Key 部分接管）与 D3（允许极小扩展点改动），实现方式：

1. 在 `ui-settings-models` 的 `ProviderEditor.tsx` 增加一个 `kind: 'single'` 的 slot 声明（例如 `settings.models.credentialNotice`），并在该 slot 有占位者时禁用 API Key 输入。**这是对现有包唯一的改动，约 10–20 行，纯扩展点，可回馈上游。**
2. 账户包在账户支持开启时填充该 slot，渲染提示文案；关闭时撤销填充，输入自动恢复可编辑。

这样"是否接管"的策略完全属于账户包，`ui-settings-models` 只提供一个中立的扩展位，不感知账户概念。

F3.13（跳过现有 DeepSeek onboarding 步骤）同理：现有步骤的判定逻辑是"任何 provider 已有可用凭据就不渲染"（见 [`ui-settings-models` README](../../packages/client/ui-settings-models/README.md)），账户登陆写入 key 后该条件自然满足，**无需额外改动**。仅需保证账户登陆引导的 `order` 早于现有的 `deepseek-official`（`order: 0`）。

| --- | --- | --- |

### 5.4 安全模型

桌面应用把 Agent 的完整能力（执行 shell、读写文件系统、访问网络）装进了用户双击就能运行的壳里，且现在还多了账户凭据，安全配置不是可选项：

| 项 | 要求 |
| --- | --- |
| `contextIsolation` | `true`，不可关闭 |
| `nodeIntegration` | `false`，渲染进程不接触 Node API |
| `sandbox` | 渲染进程开启沙箱 |
| preload 暴露面 | 只暴露 `doFetch` 与账户方法的最小集合，不暴露任意 IPC 通道、不暴露 `fs`/`child_process` |
| CSP | 禁止远程脚本与 `eval`；脚本仅来自本地打包产物与插件协议 |
| 导航 | 拦截 `will-navigate` 与 `window.open`，外部链接一律 `shell.openExternal` |
| **登陆窗口隔离** | platform 登陆页运行在**独立的 BrowserWindow 与独立 partition** 中，与应用主窗口的渲染上下文隔离；不向登陆页注入任何脚本 |
| **cookie 存储** | 登陆会话存于 Electron 的持久 partition；不把 cookie 复制到应用自己的存储 |
| **apikey 存储** | 通过已有的 `credentials.set` 写入 `$DSH_HOME/.credentials.yaml`，不另建存储；界面永不回显完整 key |
| 工具审批 | 复用既有 `packages/interaction` 权限链路，不新增旁路 |
| native 能力 | koffi 依赖必须随包正确解出，否则相关能力静默降级——见风险 R3 |

对齐 [`docs/testing.md`](../../docs/testing.md)。**原则 3 要求所有改动完成后回归验证原有功能**，具体为：

| 层级 | 内容 |
| --- | --- |

| 产物 smoke | 四个平台打包后在干净环境启动一次，验证 native 依赖已正确解出、`node:sqlite` 可用 |

## 6. 风险与缓解

| 编号 | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | **内部接口改版导致账户功能失效** | 账户功能全量不可用 | 适配层单点收敛 + 强制降级路径（F3.10）；接口探测失败时不阻塞用户 |
