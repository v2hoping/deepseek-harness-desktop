### M0 实测发现

| 发现 | 影响 | 处置 |
| --- | --- | --- |
| **Electron 拿不到 Node 的 internal ModuleLoader**（`node-addon-require-builtin` 的 `requireBuiltin` 报 `Unsupported/no-realm`）。Loader 因此回退到默认解析，所有 `@deepseek-ai/*` 行报 "Cannot find package" | 阻塞性：任何插件都装不上 | 新增 `apps/desktop/src/module-resolution.ts`，在任何行挂载前装一个只实现 `import` 的 ModuleLoader 替身，按 profile 目录解析。详见方案 5.1.3 |
| `healProfilesModuleFallback(INSTALL_ANCHOR)` 是 bare 说明符可解析的前提，CLI 在 `prepareProfile` 里调用 | 漏调则整棵树拒绝加载 | `startHost` 中显式调用；BFS 会遍历传递依赖，因此依赖 `dsh-base`（79 个插件依赖）即可覆盖 |
| `web-startup` 注入 `ctx.cmdlineArgs`，缺失则树永不 settle（表现为静默挂起，无任何错误） | 排查成本高 | `startHost` 通过 `provideCmdline` 提供空参数与 `appExit` |
| `app.whenReady().then(main, onError)` 捕获不到 `main` 自身抛出的错误 | 启动失败表现为未处理拒绝，进程存活但无窗口 | 改用 `.then(main).catch(...)`，并新增 `reportBootFailure` 递归展开 `AggregateError` 与 `cause` |
| 单实例锁获取失败时静默退出 | 残留进程持锁时，新启动无任何反馈，与崩溃无法区分 | 退出前打印说明 |
| **沙箱化 preload 必须是 CommonJS**，与包的 `"type": "module"` 冲突 | preload 作为 ESM 加载会失败 | tsdown 出两个产物：主进程 ESM `lib/main.js`，preload CJS `lib/preload.cjs` |
| `packages/client/connection/tsconfig.client.json` 用显式 `files` 列表，不是 `include` | 新增源文件不登记就报 TS6307 | 新文件需同时登记进该列表 |

## M1 功能对等

核心是需求文档 G2：**插件化能力不退化**。

实现路径与原计划不同，且更小：`__DSH_BOOT__` 注入与 `/plugins/<id>/client.js` 都由既有的 `dsh-client-modules` 提供，它只要求一个 `ctx.webServer`。因此桌面端不自建这两条能力，而是提供一个**无 socket 的路由表**（`StubWebServer`），由 Electron 自定义协议驱动——上游那套资产与插件路由被原样复用，端口仍然不开。T1.1–T1.3 与 T1.6 因此合并为下面两项。

| ID | 任务 | 规模 | 状态 | 产出物 / 结论 |
| --- | --- | --- | --- | --- |
| T1.1 | `StubWebServer`：实现 `webServer` 接缝（register / registerFallback / tapIndex / applyIndexTaps）但不监听端口，并把路由结果转成 `Response` | M | **完成** | `apps/desktop/src/web-server-stub.ts`。响应在 `writeHead` 即返回流式 `Response`——事件流永不 `end`，等它会挂死每个 SSE 请求 |
| T1.2 | 注册 `dsh://` 特权协议驱动该路由表，窗口加载 `dsh://app/index.html` | S | **完成** | 前端、资产、插件 bundle 全部由既有路由提供，`__DSH_BOOT__` 由 modules 的 index tap 注入 |
| T1.3 | 桌面 surface 的 patch 层：禁用 `webserver` 与 `client-hmr`，静默 `web-runtime` 的 URL 行 | S | **完成** | `DESKTOP_OVERRIDES`（`host.ts`）。复用 Web 名册而非另建 bundle，避免逐行跟进上游 |
| T1.4 | **插件化回归**：`ui-*` 插件在桌面端挂载与渲染 | M | **完成** | 界面完整渲染：侧边栏、工作区选择器、输入框、设置入口；渲染进程零错误 |

### 验收探针

产品路径不含它们，由环境变量选择（`apps/desktop/src/selftest.ts`）：

| 变量 | 作用 |
| --- | --- |
| `DSH_DESKTOP_SELFTEST=1` | 启动 Host、探测 `/api`、经真实渲染进程验证 IPC 载体，然后退出 |
| `DSH_DESKTOP_PROBE_CHAT=1` | 额外走一轮 Host 侧对话（`llm.models` → `session.create` → `events.mux` → `session.prompt`） |
| `DSH_DESKTOP_PROBE_UI=1` | 额外驱动真实 UI 完成一轮对话：关闭首次引导、输入、回车、轮询页面变化 |
| `DSH_DESKTOP_CAPTURE=<path>` | 写一张界面截图 |

它们放在应用内而非测试文件里，因为被测对象是一个已启动的 Electron 应用——没有测试框架能提供主进程、preload 桥与渲染进程三者。

### M1 实测发现

| 发现 | 影响 | 处置 |
| --- | --- | --- |
| **`/api` 不能直连 `toFetchHandler(apiProxy)`** | Typert channel（如 `dynamicCordisRunner`）全部 404 | `/api` 必须经 `connection` 注册的路由：那条路由在代理之前还有特权方法围栏和 Typert 拦截器。IPC 桥改为驱动整张路由表 |
| `/api` 的信任围栏按 `Host` 头判定 | 渲染进程的 `dsh://app` 不是围栏认识的授权，特权调用全被 403 拒 | IPC 请求改写为 loopback 授权——请求来自应用自身渲染进程、经网络对端无法触达的通道，这比任何头部都更强 |
| `client-hmr` 的路由持有长连接事件流，用 `res.on` | 无 socket 的路由表驱动它会抛 `res.on is not a function` | 桌面端禁用该行；打包产物本就无需热重载 |
| **patch 替换整个 `config`** | 只给 `roots` 会丢掉 `agent-presets` 的 `default`，行校验失败 | 覆盖前先经 `composeEntries` 读出原 config 再合并 |
| 改了 client 包源码后必须重建客户端产物 | 渲染进程仍跑旧 bundle，表现为改动"没生效" | `npm run build:lib:client` 后再验证 |
| **事件流不能走 `/api` 路由**：该路由对 `events.mux` / `events.host` 的普通 GET 明确答 **426 Upgrade Required**——浏览器上它们是 WebSocket 下行，路由不提供 SSE 回退 | 致命且症状极具迷惑性：unary 调用全部正常、会话能建、prompt 被接受，但**一个事件都收不到**。用户看到的是"发消息后完全没反应"，连错误提示都没有——因为错误也走事件流 | IPC 桥按路径分流：两条事件流直连 `toFetchHandler(apiProxy)` 的 SSE 编解码，其余走路由表 |
| 首次运行的欢迎引导是 modal，会 `inert` 掉 app root | composer 根本不挂载，`querySelector('textarea')` 返回 null | 既有产品行为（Web 端相同），非桌面端缺陷；探针会先关闭它，与用户首次运行一致 |

## 7. 上游跟进操作手册

需求原则 2 要求后续官方升级后仍能快速出包。做法：

### 7.1 分支模型

- `master`：保持与官方上游一致，只做 fast-forward，不落任何本项目改动。
- `feature_20260814_desktop`（及后续特性分支）：承载全部本项目改动。
- 上游发布新版本时：`master` 拉取上游 → 特性分支 rebase 到新 `master` → 跑第 6 节回归 → 重新出包。

### 7.2 改动登记表

**每一处对现有包的改动都必须登记在下表**，rebase 时逐项核对。新增的包与 `apps/desktop` 不需要登记（它们不会冲突）。

| 文件 | 改动性质 | 行数 | 是否已回馈上游 |
| --- | --- | --- | --- |
| `tsconfig.host.json` | 新增一行 `{ "path": "./apps/desktop" }` 引用（新包必须注册进一个聚合） | 1 | 否（本项目专属） |
| `packages/client/connection/src/client/ipc-api-client.ts` | 新增文件（T0.5） | — | 否（桌面专属） |
| `packages/client/connection/tsconfig.client.json` | 登记新增源文件（该配置用显式 `files` 列表） | 1 | 随上一行 |
| `packages/client/connection/src/client/index.ts` | 载体选择加一个平台分支（与既有 `?fixture` 探测同构） | ~6 | 待评估 |
| `packages/client/connection/src/client/rpc.ts` | `createWebConnectionRpc` 的 transport 改为可注入参数，默认仍是 `globalThis.fetch` | ~4 | 待评估 |
| `packages/client/ui-settings-models/src/client/ProviderEditor.tsx` | 加 slot 声明 + 占位时禁用 key 输入 | ≤20 | 待提 PR（T3.14） |

`apps/desktop/` 整个目录是新增的，不入表——它不与上游冲突。

**约束**：本表新增一行都需要在 PR 中说明为什么不能用新增包解决。表越短，跟进上游越便宜。

### 7.3 定期核对

每次 rebase 后，确认：

1. 登记表中的每一处改动是否仍然适用（上游可能已提供等价扩展点）。
2. 新增包依赖的扩展点（`settings.section`、`settings.onboarding`、`loadBundle`）是否仍然存在。
3. 第 6 节回归清单全过。
